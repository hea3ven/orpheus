Should fix · P1

The critical packages cannot reuse Go’s test-result cache

Consecutive routine runs took 27.24s and 27.07s because internal/cli and internal/git executed again instead of returning (cached). Cache diagnostics produced different input IDs on every run; the fingerprints include random temporary working directories and broad repository scans. The CLI tests still contain 13 t.Chdir calls, while CLI and Git boundary tests walk the repository and exclude only .git and vendor.

Impact: the fastest developer feedback loop repeatedly pays the full subprocess and filesystem cost. A no-test-body control completes in 2.35s, so restoring cacheability could move unchanged repeat runs much closer to that floor; the exact gain needs validation after the inputs are narrowed.

Observed: a warm repeat used 30.64s user CPU and 38.74s system CPU over 27.07s wall time. System time is 56% of total CPU time, consistent with process- and filesystem-heavy tests rather than pure Go computation.
Should fix · P1

The lane names classify safety and one dependency, not test scope

make test runs every untagged test and is called “hermetic,” while make test-integration selects only real-Beads scenarios. The fast lane therefore includes 45 real-Git contract tests, five explicitly named CLI end-to-end completion flows, and broad cross-package workflow tests alongside package-local units.

Impact: developers cannot select a genuinely unit-scoped feedback loop, and “integration” is incorrectly read as permission to use credentials, networks, operator data, or real model agents. Those are safety prohibitions for every automated lane, not classification criteria.

Current inventory: 862 top-level tests across 90 files; 853 are untagged and only 9 are tagged integration tests. Forty-three test files make direct filesystem calls, 50 allocate temporary directories, and 9 call os/exec directly; indirect helper and production calls widen all three footprints.
Should fix · P2

Test cost has a baseline; coverage value does not

The repository tracks timing budgets and JSON timing artifacts, but has no coverage target, normalized profile, baseline, or merge-base comparison. That makes it impossible to see whether a costly new scenario reaches new production statements, merely repeats an existing path under a different adapter, or loses coverage elsewhere.

Impact: test additions can increase wall time without making their marginal value visible. Add a coverage companion to cmd/testtiming, but treat overlap as a review signal—not proof that a scenario is redundant—because Go statement coverage cannot observe assertion strength, input partitions, external-tool semantics, branches, or failure behavior.

Hermetic does not mean unit

make test runs every non-integration-tagged test. The lane mixes genuine unit tests with filesystem-backed component tests, real-Git adapter contract tests, and named end-to-end completion scenarios. Network access, credentials, operator data, and model-provider calls must be forbidden in every automated test lane; they are safety invariants, not the line between unit and integration.

Classification audit: use three independent axes

A useful name must answer what is under test without hiding how it runs. The current “hermetic versus real Beads” split combines unrelated concerns and leaves most integration tests in the fast lane.

Axis 1 · scope

Unit or integration

Does the test target one package’s behavior behind collaborator seams, or verify collaboration across packages / an adapter contract?

Axis 2 · medium

Memory, disk, or process

A unit can legitimately use disk when filesystem semantics are its subject. Record the medium separately because it predicts cost.

Axis 3 · safety

Isolated or live

All automated tests are isolated: no external network, credentials, operator data, or Codex/Pi provider calls. Live evaluations remain outside test validation.

Unit test

Targets behavior owned by one package. Other Orpheus services are values, fakes, or injected interfaces; no child process is required. It may be memory or disk when testing paths, encoding, atomic replacement, locks, or permissions.

Integration test

Verifies a collaboration across Orpheus packages or a contract with an actual local adapter such as Git, Beads, gh, the OS process environment, or the compiled CLI. It is usually disk process but remains fully isolated.

Coverage economics: measure reach and marginal reach

Coverage was measured at a56e569 with Go statement instrumentation and -coverpkg=./..., then normalized by source block. Cross-package instrumentation is essential for workflow tests; normal package-local coverage would credit only the package containing the test. The raw fast profile repeated blocks for each test binary—281,900 data rows collapsed to 12,813 unique source blocks—so a comparison tool must merge counts before calculating overlap.

Publish two primary coverage values

The stable interface should report unit coverage and integration coverage separately, each against the same complete production-statement denominator. Combined coverage and integration-marginal coverage are useful derived diagnostics, but they must not replace the two lane values. The present 77.7% result is labeled fast, not unit, because classification has not yet moved the many Git, CLI, and workflow integrations out of that lane.

High overlap is a question, not a deletion verdict

The integration tests’ primary value is validating real process and Beads contracts, not increasing statement coverage. Two tests may execute identical Orpheus statements while proving different input partitions, output assertions, persistence effects, or external-tool compatibility. Use marginal coverage to identify scenarios for semantic review; consolidate only after comparing their contract and failure-detection value.
