Cost investigation / Codex harness → Pi harness

The cost rose in review, not in implementation.

A four-day before/after analysis of Orpheus tasks and 316 execution records finds a 37.0% increase in estimated API-equivalent cost after the July 16 harness switch. The dominant mechanism remains extra reviewer model turns replaying cached context.

Equal windows Pre: 12–15 July
Post: 16–19 July
Cutover: 16 Jul, 08:47 CEST
Model: GPT-5.5 / high thinking
Executive verdict

The switch is associated with a real cost increase, but “Pi makes every run more expensive” is false. Implementation cost per execution fell 12%. Review cost per execution rose 48%, review executions rose 21%, and 77% of the total dollar increase came from additional cached-input tokens. Worse first-pass implementation quality contributed, but serial one-finding review cycles were the larger cycle multiplier.

05 / Cycle cause

Initial output was weaker. Serial discovery multiplied the damage.

The post-switch implementations did reach review with more real defects, but that explains only part of the extra cycling. The stronger signal is that independent findings were commonly delivered one review at a time, with architecture review deferred until the general reviewer passed.

Causal assessment

Candidate causeEvidence in the sessions and task recordsAssessment
Worse initial implementation output Only 4 of 15 post cohorts passed first review, versus 8 of 19 pre. The blockers were usually concrete correctness, acceptance, security, or ownership defects, and 54 of 56 post-window AI blockers in the attempt records were linked to a repair run. Real, meaningful contributor.
Better or more detailed reviews Post AI blocker descriptions were slightly shorter (110 vs 121 words on average; median 97 vs 106), and blockers per blocked attempt fell from 1.31 to 1.15. The findings were useful, but each individual review was not more exhaustive. Not supported as the main explanation.
Serial finding discovery 50 of 59 post blocked attempts contained exactly one blocker. Repaired tasks that eventually passed averaged about two more attempts than before. General-review blockers stopped the pipeline before architecture review in 35 post attempts, so architectural defects could only surface later. Largest review-cycle multiplier.
Operational and check churn Post attempt records contain eight failed and three aborted reviews versus one aborted review pre-switch. server-8j9.1 alone had repeated check failures after substantive security and packaging findings. Smaller, visible contributor.
Harder post-switch task mix The most expensive post tasks crossed workflow, task-state, diagnostics, Git, publication, and security boundaries. These broad changes create more independent failure surfaces than the window average. Likely amplifier; not separable observationally.

Best reading: implementation quality deteriorated enough to create more entry into repair loops, while the review pipeline and Pi's less-batched interaction style stretched those loops. The data does not show a simple trade of “higher cost for more detailed reviews.” It shows valid findings arriving less exhaustively per pass.

07 / Conclusions

What the evidence supports.

Confidence reflects the strength of the local evidence, not statistical certainty from a randomized experiment.

  1. The increase is real in Orpheus's estimate High confidence

    Equal windows show +37.0% cost and +51.2% tokens. All 163 priced Pi executions reproduce exactly under the same GPT-5.5 formula used for Codex; the harness did not silently select a more expensive pricing row.

  2. Reviewer interaction is the primary mechanism High confidence

    Review accounts for 86.4% of the net increase. Pi review sessions made 83.7% more model turns but 10.9% fewer tool calls, halving tool calls per turn. This repeatedly replayed cached context.

  3. Weaker implementation output started more loops High confidence

    The first-pass approval rate fell from 42.1% to 26.7%. Most AI blockers were concrete defects linked to a subsequent repair, so the difference is not explained by cosmetic feedback or obvious review noise.

  4. Serial discovery stretched those loops High confidence

    Post blocked attempts were more likely to return exactly one finding, not more findings or longer descriptions. General-review failures also deferred architecture review. This is stronger evidence for serialized feedback than for uniformly deeper reviews.

  5. Pi is not uniformly more expensive High confidence

    Implementation token volume per session was flat and implementation cost per execution fell 7%. The cross-boundary server task also had materially cheaper Pi implementation runs.

  6. The exact causal share needs a matched A/B test Medium confidence

    The windows contain different tasks and evolving review code. The session mechanics strongly implicate the harness, but observational data cannot cleanly separate Pi behavior from harder diffs and stricter review outcomes.

08 / Actions

Measure round trips, then reduce them.

The best next steps preserve review quality while targeting the specific source of cost: model round trips over repeated context.

01

Add turn and tool-call telemetry

Persist model-turn count, tool-call count, and cached-token share per execution, grouped by purpose and profile. Cost totals alone hide the batching failure.

02

Batch inspection and report all blockers

Ask both Pi reviewer profiles to batch independent reads and complete a whole-diff pass before returning. The logs show neither tool-call batching nor finding batching is used consistently.

03

Run a matched review A/B

Give Codex and Pi the same frozen diff and review prompt, 5–10 repetitions each. Compare findings, turns, cached tokens, cost, and false-positive rate separately for general and architecture review.

04

Track quality-adjusted cost

Do not optimize solely for dollars. Report cost per passed review, blocking findings confirmed by fix, first-pass approval, repair cycles, and resolution so cheaper but weaker review is visible.

05

Consolidate general and architecture feedback

Run architecture inspection even when general review finds blockers, then repair one consolidated finding set. Preserve separate verdicts, but avoid making each reviewer wait for the previous gate to pass.

06

Keep telemetry caveats visible

Separate harness-reported estimates, Orpheus-calculated estimates, and invoice/subscription cost. Keep unknown execution coverage beside every cost view.

09 / Method

Sources, normalization, and limits.

This is a reconstruction from current local state and raw session logs, not a vendor invoice reconciliation.

Telemetry discontinuity

Pi usage initially failed to parse because usage lives under message.usage. The July 18 fix and Doctor recovery backfilled 157 Pi executions. All recovered records have capture timestamps on or after July 18.

Coverage

Pre: 141/144 executions have usage and cost. Post: 164/172. Unknown failed/unmatched executions remain in execution counts but contribute neither tokens nor cost, slightly understating both windows.

Token semantics

Codex records cached input as a subset of input; Pi records uncached input and cached input separately. The analysis normalizes these before decomposition. Total-token values are comparable after normalization.

Local evidence used

  • orpheus task stats --group daily, plus consumption, throughput, implementation, and review views across all registered repositories.
  • Task execution state under ~/.local/share/orpheus/repos/*/tasks/*.yaml, including runs, review steps, usage, cost, findings, repair links, and resolution events.
  • Raw Codex sessions under ~/.codex/sessions and Pi sessions under ~/.pi/agent/sessions.
  • Review-cycle audit of attempt outcomes, blocker descriptions, pipeline stopping points, and explicit SKILL.md reads in each correlated review session.
  • Beads records for exact task titles and resolution dates.
  • Current config and timestamp at ~/.config/orpheus/config.yaml.
  • Orpheus source and Git history, especially Pi capture commit aa1a0d4 (15 Jul) and nested-usage fix b76528d (18 Jul).

Important limitations

  • Costs are estimated API-equivalent costs. They may not equal Codex subscription usage, credits, or a vendor invoice.
  • The comparison is observational. Task complexity, review strictness, and Orpheus code changed at the same time as the harness.
  • A repair link shows that a finding triggered implementation work; it does not independently prove that every finding was necessary or optimally scoped.
  • The review summary anchors whole task cohorts on first review activity; the forensic cycle section anchors individual attempts on attempt time. Their finding counts intentionally answer different questions and therefore do not match exactly.
  • Execution-day cost and resolution-day throughput use different anchors; window efficiency ratios should not be read as exact per-task attribution.
  • Task state reflects Doctor recovery performed after the original runs. That improves completeness but means the report is a reconstructed view.
