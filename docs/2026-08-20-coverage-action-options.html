Coverage without the churn.

A repository-specific investigation into the failing baseline, repeated test cost, stacked/behind-base branches, and better ways to keep coverage useful.

No commit hook
Executive decision

Separate correctness from coverage observation.

The current job combines three jobs with different lifecycles: test correctness, exact baseline freshness, and coverage comparison. The exact-freshness requirement is the source of most noise. A commit hook would only move that noise onto every developer machine.

Recommended direction

Lean required CI on every PR; full coverage off the commit path.

Run unit and integration tests once for correctness, cancel superseded runs, and retain useful failure output. Move the two-sample classified coverage report to a nightly/manual workflow, remove the 9.8 MB tracked baseline, and compute a comparison only when somebody asks for it. If automated patch coverage later proves valuable, let a coverage service store the history instead of Git.

Unavoidable trade-off: GitHub required checks must pass against the latest commit. A coverage gate that is required and current therefore has to run for each updated PR SHA. The only way to stop per-commit coverage runs is to make coverage non-required or move it to a different trigger.

More than half the successful runtime is setup

Successful runs spent 2:34–3:19 compiling/installing Beads and installing Dolt, then 2:08–2:38 collecting coverage. The current tool cache does not prevent the large Beads install from dominating the job.

Baseline updates swamp ordinary diffs

Recent feature work changed the baseline by roughly 14k–34k lines per refresh. PR #104 carries 10,366 baseline additions and 9,668 deletions beside 567 lines of product, test, and documentation changes.

Failures are hard to diagnose

Two runs failed in integration coverage, including PR #104 after its baseline was refreshed. The visible error is only run integration coverage sample 1: exit status 1; because collection exits before writing the report, the always-upload step finds no artifact.

This is currently the repository’s only Actions workflow

Deleting it outright would also delete hosted PR test feedback. The useful replacement is a small correctness workflow, not a CI vacuum.

Dataset: the 12 runs returned for test-coverage.yml on 19–20 August 2026: 3 success, 9 failure. Seven failures explicitly reported stale/invalid baselines; two exited during integration coverage. Timings come from successful job step timestamps. Repository metrics come from the checked-in baseline and Git history.

Root cause

The job checks one tree against an artifact made for another.

On a pull_request event, GitHub checks out refs/pull/<n>/merge by default—the synthetic result of merging the current base into the PR head. The tool then requires the baseline file inherited from the PR branch to exactly match that merged tree before it will compare against the base baseline.

STEP 01

Commit or base update

A PR commit, stacked branch change, or base-branch advance creates a new merge SHA.

STEP 02

Merge tree checkout

Actions tests the synthesized base + head tree, not merely the branch head.

STEP 03

Four test executions

Unit twice, integration twice, all serial and instrumented with -coverpkg=./....

STEP 04

Exact freshness gate

Test count, source blocks, aggregates, commands, and hit states must all equal the PR file.

STEP 05

Refresh and retry

Generate ~10 MB locally, commit a huge diff, push, and spend another five to six minutes.

Why merging main is especially irritating

The merge changes the effective source/test tree even when the feature itself is untouched. That legitimately changes source-block coordinates, fingerprints, denominators, test counts, or hit states. The current policy treats any such drift as a contributor error.

Why a commit hook does not fix it

A hook cannot predict the future synthetic merge tree. It also adds four full-suite invocations to local commits, creates environment-dependent generated diffs, and can be skipped. It automates the symptom while preserving the coupling.

Target operating model

Two lanes, two promises.

The required lane answers “does this merged change work?” The observation lane answers “where is our coverage moving?” Neither pretends to be the other.

Required · each current PR SHA

Correctness CI

  1. Checkout the synthetic merge commit intentionally.
  2. Run unit tests once and integration tests once; keep lint/build as appropriate.
  3. Preserve complete failing test output and upload diagnostics.
  4. Cancel superseded runs for the same PR.
  5. Cache or download the pinned Beads binary instead of rebuilding its dependency graph every run.
Non-required · nightly + manual

Coverage observation

  1. Keep the current classified unit/integration model and two-sample union if its stability is worth the cost.
  2. Write JSON/HTML to a workflow artifact; do not commit generated hit-state inventories.
  3. Trend main over time. For an occasional PR comparison, compute both selected base and target in that run.
  4. Retain the scenario audit as explicit on-demand work.
  5. Escalate to Codecov only if automated patch deltas become worth per-commit coverage again.

Do not require a path-filtered workflow

GitHub leaves a workflow skipped by path filtering in Pending when that workflow is required. Use an always-created required job with internal conditions, or do not path-filter the required workflow.

Key comparisons by immutable SHA

Branch names move. Any cached or uploaded base report must be identified by the exact base commit plus Go/tool/schema versions, with regeneration on a miss.

Never discard failing test output

The collector should retain decoded go test -json failure events and write a partial diagnostic report before returning an error.

Proposed migration

Small reversible steps, no hook.

Stop wasting obsolete runs

Add PR-scoped concurrency with cancel-in-progress: true. Make current failure output visible. This is useful under every later option.

Low risk · first

Introduce lean correctness CI

Run each lane once. Measure its real hosted duration, and cache/download the pinned test tools. Make this the required check before weakening coverage.

Low–medium risk

Move coverage off PR synchronize

Change full coverage to scheduled + manual, mark it non-required, and keep report artifacts. Confirm one week of clean correctness CI.

Policy change

Remove the tracked baseline

Teach cmd/testcoverage to report without an implicit freshness check, then delete the generated baseline and update testing documentation.

Repo cleanup

Review after two weeks

If reviewers miss automatic deltas, trial Codecov or exact base/target computation. Decide with measured run time and actual review usage, not theoretical completeness.

Evidence gate

Success criteria: no contributor-authored coverage refresh commits; a normal PR receives actionable correctness feedback in roughly the duration of one integration lane rather than four instrumented suite runs; merging main into a branch does not demand repository changes; full coverage remains available within one deliberate action.
